# Bundled rsvp model Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship `system/models/rsvp/` so any item of a site's events collection takes replies: yes (with a party size), no or maybe. A yes that doesn't fit goes on a waitlist, and the model moves people in as places free up. Every guest email carries a link to change the reply, and a GET of it changes nothing. Staff see each event's counts and replies on a Records-recipe page and add phone replies there. A site writes no model code, and the demo café's events take replies.

**Architecture:** One bundled model, `rsvp`, declares one private record type, `rsvp`, through `types()`. It counts only where a view uses `render.rsvp.*` or `print.rsvp.*`. The event stays an item of a markup collection (`rsvp_collection`, `events`): the model reads its `date`, `starts`, `places` and `rsvp_until` with `cms_store::get_item()` and never writes it. `fill()` works out each reply's `status` from its `answer` and the places, and `check()` guards the places, all inside the write's transaction. Promotion from the waitlist runs in the same transaction when the model makes the change, and in a transaction of its own from the `cms.item_saved` / `cms.item_deleted` listeners when staff edit a reply or the event in the page. Tokens, the manage page, the email sending, the region options and the guarded model write are rsvp's own code, written again after booking's. **Nothing is shared with booking or contact, and neither is touched.**

**Tech Stack:** PHP 8.1+ in Raster style (no namespaces, types, `[]`, `match`, arrow functions; tabs), RedBean, SQLite and MySQL, `cms_records`, `cms_store`, plain-PHP tests (`test()`, `check()`, `same()`).

**Spec:** `docs/designs/rsvp.md` (approved 2026-10-20; its eight decisions are final, Decision 3 taken as "no shared code"). Written against 2.2.13; this plan is written against master at 2.2.29 (booking B4, the spam checks and the contact model merged). Tracking: #168 Phase 2.

## Global Constraints

- STYLEGUIDE.md in full: `array()`, no type declarations, static hooks, lowercase snake_case, a `/** */` header on the bundled model, `//` comments that say why.
- **No shared code (Decision 3).** `git diff master -- system/models/booking system/models/contact` stays empty in every PR. rsvp has its own `issue()`, `by_token()`, `$links`, `manage()`, `manage_done()`, `send()`, `options()`, `writing()`, `payload()`, `ready()` and `requires()`. It may call the framework core: `cms_records`, `cms_store`, `cms_types`, `mail` (through `controller::model_class('mail')`), `validation`, `validation_spam`, `util`, `controller`, `event`, `raster_cache`, `authentication`. It never calls `booking::` or `contact::`.
- No new dependency. SQL lives in `system/models/rsvp/sql/*.sql` and runs as `database::instance('rsvp')->name(...)`. Records go through `cms_records` only. The one exception is reading the events collection, whose table name comes from a setting (`<rsvp_collection>data`): that SQL is put together in PHP, with the name checked against `/^[a-z][a-z0-9_]*$/` and every value bound.
- SQL takes PHP's clock as arguments (`date('Y-m-d H:i:s')`), never `date('now')` or `NOW()`. Deadlines and "has it started" are real seconds: `strtotime("$date $starts")` in the site's `timezone`.
- Problem and alert names are literals (`$problems[] = 'closed'`, `cms_records::refuse('not_waiting')`, `$v->raise('already_replied')`) so `lint` knows they are raised.
- The template owns every word. The model returns rows, `false`/`null`, or names.
- **Anti-goals are tests:** no JavaScript needed; a GET changes nothing; no token, email or phone in a slug, a public page, a log, an event payload or the page cache; two posts can't both take the last place; a freed place never stays empty while someone who fits waits (before the deadline); nobody `going` is ever moved out by someone else's change.
- `tests/run.php`'s "a page request loads nothing from `system/tools/`" keeps passing: reading the event never goes through `cms::collection_example()` or the inspector. A site that doesn't use rsvp loads no file from `system/models/rsvp/`, gets no `rsvpdata` table, and sees nothing new in `describe`, Admin or MCP. A site using rsvp and not booking loads nothing from `system/models/booking/`, and the reverse.
- AGENTS.md changes go in the same commit as the behaviour. Each PR documents its own part; R5 finishes "Bundled models: rsvp" with the step-by-step and the worked staff page.
- A new demo-visible feature gets an ID in `demo/README.md`. The next free letter is **S** (A–R and T are taken).
- Each PR is its own release: the next 2.2.x when it merges (master is at 2.2.29; #212 claims 2.2.30). Writers add the CHANGELOG section under a `## 2.2.x` heading the merger numbers; the merger bumps `system/VERSION` and the three `config/raster-version` files (`application/`, `demo/`, `shop/`).
- Each PR branches from the previous one: `rsvp/r1-places` (from `master`, once this plan is merged) → `rsvp/r2-link` → `rsvp/r3-form` → `rsvp/r4-staff` → `rsvp/r5-demo`.
- This server goes down under parallel test suites: run ONE suite at a time, in the foreground; focused runs (`RASTER_TEST_ONLY=…`) while iterating; the full suites (run.php, demo.php, shop.php, update.php, both lints) once, one after another, before a commit; check `pgrep -af 'php.*-S 127.0.0.1'` after each and kill only your own leftovers. Never run tests/mutate.php.

## Decisions (plan's calls, where the design is silent)

1. **Who is writing.** `rsvp::$acting` is `'guest'`, `'staff'` or `'waitlist'` around the model's own writes, set by `writing($who, $id, $work)` (rsvp's copy of booking's: one `cms_records::transaction`, `$acting` and `$writing` put back in `finally`, `unset(self::$links[$id])` on a throw). `rsvp::is_staff()` is true when `cms_records::writer()` is `'editor'`, or `'model'` with `$acting !== 'guest'`. A form post is writer `'visitor'`: a guest. Model code that calls `cms_records::create/update('rsvp', …)` itself is trusted like staff, and its replies get `rsvp.replied` with `who` `staff` from the listener.
2. **The `rsvp` type**, fields in this order (the slug comes from `name`, which is required, so never from the email): `name` '', `email` '', `phone` '', `event` 0, `answer` 'yes', `people` 1, `notes` '', `status` '', `waiting_since` '' (datetime), `changed_at` '' (datetime), `event_at` '' (datetime), `token_hashes` array(), `link_sent_at` '' (datetime). `readonly`: `status`, `waiting_since`, `changed_at`, `event_at`. `hidden`: `token_hashes`, `link_sent_at`. `create` visitor, `staff_add` true, `owner` true, private, the spam checks on (the default), actions `promote` => editor. `event` stays writable so the new-item card at the end of `render.cms.rsvp('event=?event&…')` starts with it.
3. **A visitor never chooses the event.** `cms_records::submit()` writes every writable field the post has, `event` included. So `fill()` sets `event` to `rsvp::$posting` (the page's event, which `form()` sets) on every `'visitor'` write, and to 0 when nothing set it, which `check()` refuses as `not_open`. Tests that write as a visitor in-process set `rsvp::$posting` themselves.
4. **`event_at` is a field the design doesn't list.** The design flags `moved` "from `changed_at`", but `cms.item_saved` carries only the item after the save (`store.php:525`), not before, so a change of date can't be told from a typo fix. `fill()` stores the event's start (`date starts`, as a datetime) in `event_at` on create, when `event`, `answer`, `people` or `status` change (the guest was told the time then), and on any write by an editor (so staff clear the flag by saving the reply, a note "phoned them" in `notes`). `moved` is `event_at` not empty and not the event's start now. R4 also uses it to find replies to a deleted event that was still to come.
5. **Reading the event.** `rsvp::event($id)` → `null`, or `array('id', 'title', 'slug', 'date', 'starts', 'places', 'rsvp_until', 'visible', 'starts_at', 'deadline', 'url')`, kept per request (`forget()` clears it; `fill()` calls it first, as booking's does, so the write's lock reads fresh). `title` is `cms_store::slug_source($item)`. `starts` is the item's `starts`, else its `time`, else `00:00`, cut to `H:i` (MySQL gives `H:i:s`). `places` is `(int)`, 0 for empty. `visible` is `enabled` not `0` and `published_at` empty or not after now, as `cms_store::published_sql()` decides. An item with no `date` is `null`. `url` is `util::url("<c>/<c>_item/<slug>")`.
6. **The deadline** is `rsvp_until` when the item has one, else the start minus `rsvp_closes` minutes, and never later than the start: `min($until ?: $start - $closes * 60, $start)`. Before it anything goes; from it until the start a guest only gives places back; from the start a guest changes nothing.
7. **Which event a page is about.** `rsvp::page_event()`: on `/<c>/<c>_item/<slug or id>` the item as `render.cms` finds it (a number is a slug first, #90, `cms.php:400`); else `?event=<digits>`; else null. Read once per request. An event visitors can't see is null for a visitor; editors get it, so they can check the page of a draft.
8. **`fill()`'s status rules**, on every write (`$e` the event, `going()` the people going without this reply):
   - `answer` `no` → `no`, `maybe` → `maybe`, both with `waiting_since` ''.
   - `yes`, same event, and `$before['status']` is `going` → stays `going` (a bigger party is `check()`'s `full_for_more`).
   - `yes`, same event, and `$before['status']` is `waiting` → stays `waiting` and keeps `waiting_since` (a smaller party keeps its place in the queue; promotion then moves it in if it fits).
   - any other `yes` (new, from no or maybe, or moved to another event) → `going` when `$e['places']` is 0 or `going() + people <= places`, else `waiting` with `waiting_since` now.
   - A write by the model that names `status` itself (promotion, the action) and changes no `answer`, `people` or `event` keeps that status.
   - `changed_at` when `status` or `people` change. A going reply that stops being going, gets smaller or moves to another event notes `rsvp::$freed[<event>] = true` (the old event when it moved), so the change's writer promotes there. A staff write also notes `rsvp::$changed[$id] = array('was' => …, 'was_people' => …)` for `saved()`.
9. **`check()`'s rules**, in this order, run on create and when `answer`, `people`, `event` or `email` change (any other edit goes through): `not_open` (no event, no `date`, or hidden from a visitor), `name_invalid` (empty, a control character, over 200), `email_invalid` (a guest's empty; anyone's not `FILTER_VALIDATE_EMAIL`, a control character, over 254), `answer_invalid`, `people_invalid` (a yes below 1), `too_many` (a yes over `places` for anyone, or over `rsvp_max_people` for guests), `closed` (a guest, from the deadline: a new yes, a no or maybe becoming yes, or more people; from the start: any change), `full` (newly `waiting` while `rsvp_waitlist` is false), `already_replied` (another reply to this event with this email, lowercased; `sql/replied.sql`). Then, whatever changed, a write that makes a reply `going` or makes a going party bigger must fit: `full_for_more` when it was going and grew, `not_enough_places` otherwise (a promotion or the action that lost a race).
10. **SQL files:** `going.sql` (`SELECT COALESCE(SUM(people), 0) AS going FROM rsvpdata WHERE event = ? AND status = 'going' AND id != ?`), `queue.sql` (`SELECT id, people, waiting_since FROM rsvpdata WHERE event = ? AND status = 'waiting' ORDER BY waiting_since, id`), `replied.sql` (`SELECT id FROM rsvpdata WHERE event = ? AND LOWER(email) = ? AND id != ?`), `by_token.sql` (`SELECT id, token_hashes FROM rsvpdata WHERE token_hashes LIKE ?`), `counts.sql` (`SELECT event, status, COUNT(*) AS replies, COALESCE(SUM(people), 0) AS people FROM rsvpdata WHERE event >= ? AND event <= ? GROUP BY event, status`). Each caller skips the query while `rsvpdata` doesn't exist.
11. **Promotion** (the design's Decisions 4 and 5), the one algorithm with a body here. The queue runner is `promote_waiting($id)`, because the type's action is named `promote` and an action is a static method of that name (`promote($item, $input)`):

    ```php
    // Moves in, oldest first, every waiting reply whose party fits: a party
    // of 4 that doesn't fit doesn't keep two places from a couple behind it.
    // Inside the write's lock and reading everything again, so a second run
    // moves nobody. Nothing from the deadline, or for an event visitors
    // can't see: freed places are staff's to give then (the promote action).
    static function promote_waiting($id) {
    	return self::writing('waitlist', 0, function () use ($id) {
    		self::forget();
    		$event = self::event($id);
    		if (!$event || !$event['visible'] || time() >= $event['deadline'] || !cms_store::table_exists('rsvpdata')) return array();
    		$left = $event['places'] > 0 ? $event['places'] - self::going($id, 0) : null;
    		$moved = array();
    		foreach (database::instance('rsvp')->queue($id) as $row) {
    			if ($left !== null && $left < 1) break;
    			if ($left !== null && (int)$row['people'] > $left) continue;
    			$reply = cms_records::get('rsvp', $row['id']);
    			// R2 adds self::issue($reply) to these values: the promoted guest's new link
    			$saved = cms_records::update('rsvp', $reply['id'], array('status' => 'going', 'waiting_since' => ''));
    			cms_records::dispatch('rsvp.promoted', self::payload($saved, 'waitlist'));
    			if ($left !== null) $left -= (int)$saved['people'];
    			$moved[] = $saved;
    		}
    		return $moved;
    	});
    }
    ```

    Inside another transaction (a guest's change) `cms_records::transaction` joins it, so the change and the promotions commit or roll back together.
12. **Where promotion runs.** The model's own writes (`change()`, the `promote` action, `form()` never: a new reply frees nothing) call `promote_waiting($event)` for each `rsvp::$freed` event before their transaction ends. The listeners run it after the commit: `saved()` on `cms.item_saved` for an item of `rsvp_collection` (any save: places raised or emptied, the event published again; a second run is harmless), and for an `rsvp` the model didn't write itself (`!self::$writing`) with `$freed` set; `deleted()` on `cms.item_deleted` for a going `rsvp`. Deleting an event promotes nobody (its replies are `event_gone`).
13. **Events and payloads.** `payload($reply, $who)` = `cms_records::shown(info('rsvp'), $reply)` (no hidden fields) + `who` (`guest`, `staff` or `waitlist`) + `event_title`, `event_date`, `event_starts` (empty when the event is gone). `rsvp.replied` on create; `rsvp.changed` when `answer`, `people` or `event` changed, with `was` and `was_people`; `rsvp.promoted`. The model's own writes dispatch them inside `writing()`; `saved()` dispatches them for staff's and model code's writes (`who` staff). All go through `cms_records::dispatch`, so they wait for the commit.
14. **Tokens** (R2), rsvp's copy of booking's scheme without `token_expires`: `bin2hex(random_bytes(32))`, `hash('sha256', $raw)` appended to `token_hashes`, the newest 20 kept, the raw token in `rsvp::$links[$id]` for this request only. `by_token($raw)`: `/^[a-f0-9]{64}$/`, `by_token.sql` with `'%'.$hash.'%'`, then `hash_equals` over the decoded list, then `is_live()`: the reply's event exists, is visible and hasn't started. Any status is live: a `no` reply's link still works.
15. **Which guest email** (R2), decided by the listeners from the payload: `rsvp_promoted` for `rsvp.promoted`; else by `status` against `was` / `was_people`: `going` and (was not going, or people changed) → `rsvp_going`; `waiting` and (was not waiting, or people changed) → `rsvp_waiting` (a waiting party's new size gets the waiting email again, with its position); `no`/`maybe` and was another status → `rsvp_noted`; anything else → none. A write issues a link only when it sends an email, in the same `update` (`issue()` merged into the values, or a second `update` in the same transaction after `submit()`). `rsvp_new` to `rsvp_staff_email` for `replied` and `changed` with `who` guest, only when that setting is set. `rsvp_link` is not an event's email: `form()` sends it itself after its write commits (Decision 19).
16. **Email vars:** the payload, `manage_url` (`util::url(rsvp_manage_page, array('token' => $raw))` when `$links[$id]`, then unset; `''` otherwise and always for staff), `position` (1 + the waiting replies of the event queued before it, `''` unless waiting), `event_url`, `deadline` (`Y-m-d H:i`), `site_url`. `send($view, $to, $vars)` is rsvp's copy of booking's: through `controller::model_class('mail')`, a failure logged as `rsvp: <view>: <error>` without the address or the link.
17. **The manage page** (R2): `render.rsvp.manage` by `?token=`, or a logged-in owner's `?reply=<id>` (`cms_records::owner_me()`). Always `raster_cache::skip()` and `Referrer-Policy: same-origin`. A GET (or HEAD, or a GET with `do=change` in the query) changes nothing. A POST `do=change` with `answer` and `people` runs `rsvp::change($id, $values, 'guest')`; the same answer and people again writes and sends nothing. After a change it redirects to `?done=changed` without the token (the owner's keeps `?reply=`). Refusals (`closed`, `full_for_more`, `full`, `too_many`, `people_invalid`, `answer_invalid`) are raised and the row comes back. An event that has started, is hidden or is gone: `link_invalid`, also on a POST.
18. **The form** (R3) is `cms_records::submit('rsvp', false)` inside `writing('guest', 0, …)`, with `rsvp::$posting` set to `page_event()`'s id. Shown first, it raises `not_open` when the page has no event visitors can see (or no `date`), and `closed` when the deadline has passed. A stored reply redirects to `?done=going`, `?done=waiting` or `?done=noted` (by its status) on the page it was sent from, keeping `?event=` when the event came from it (`util::done($name, $location)`; `util::done()` alone drops the query).
19. **`already_replied` and the link again** (R3). In `form()`, after `valid()` and the spam hold, before `submit()`: `replied.sql` for this event and the posted email (lowercased). A match raises `already_replied`, returns `form_state()`, and, unless `mail::sent_lately($reply['link_sent_at'])`, writes `issue()` + `link_sent_at` now to that reply and sends `_email/rsvp_link` to **the reply's own address**. `check()` refuses `already_replied` too, for two posts at once and for staff adding a second reply; that path mails nothing.
20. **Spam checks** (2.2.23–2.2.29). `render.rsvp.form`: stamp and limits, no text checks, as the booking form. `cms_records::submit()` asks `validation_spam::holds($v->suspect(array()))` already; `form()` asks the same first, before the `already_replied` lookup, so a script can't use that path to mail a link without a stamp and the per-email limit (`spam_per_email`, 3 an hour) stops a mail-bombing loop on the 4th post. `suspect()` counts a post once however often it is asked. Over `spam_per_ip` alone a reply is taken (flagged, not held) unless `spam_ip_blocks`. `render.rsvp.manage` and the `promote` action aren't checked, as booking's manage page isn't. `validation_spam::$checked_regions` gains `render.rsvp.form`, so `lint` warns on a view (with what it includes) lacking `print.validation.alert('try_again')` or `('slow_down')`. The café's `_layout.html` `res.header` has both already.
21. **Staff regions** (R4) give `array()` / `''` to anyone but editors (`''` as contact's count does, the newest model) and call `raster_cache::skip()`. `render.rsvp.events($options = 'from=today')` reads the events with `date >= from` in one query on `<c>data` (drafts and scheduled ones included: staff need to see what they hid), ordered by `date, starts`, then their replies with one `cms_records::find('rsvp', "event>=$min&event<=$max&order=waiting_since,created_at")` and the counts with `counts.sql`, grouped in PHP. `render.rsvp.attention`: active replies (`going`, `waiting`) with a reason, to events to come, plus replies to a gone event whose `event_at` is today or later. Reasons, first that applies: `event_gone`, `event_hidden`, `over_places`, `moved`.
22. **`requires()`** (grown per PR): `emails` `render.rsvp.form` ⇒ `_email/rsvp_going`, `rsvp_waiting`, `rsvp_promoted`, `rsvp_noted`, `rsvp_link` (+ `rsvp_new` when `rsvp_staff_email` is set); `render.rsvp.manage` ⇒ the first four. `pages` `rsvp_manage_page`. `settings` the six `rsvp_*`. `lists` `rsvp` ⇒ `render.rsvp.events`.
23. **lint:** an error on a view with `render.rsvp.form` when the `rsvp_collection`'s content model has no `date`, and a warning when it has no `places` ("no limit, so no waitlist") (R3); a warning when a view with `render.rsvp.manage` is an admin view ("never protect rsvp") (R2); a warning when a view with `render.rsvp.events` or `render.rsvp.attention` isn't (R4). Severities as booking's (an "error" is `error`, a "notice" is `warning`).
24. **Bindings** in `system/config/events.php`, only when `controller::model('rsvp')['bundled'] && controller::uses('rsvp')`, after contact's block: `cms.item_saved` → `saved`, `cms.item_deleted` → `deleted` (R1); `rsvp.replied` → `replied_mail`, `rsvp.changed` → `changed_mail`, `rsvp.promoted` → `promoted_mail` (R2).
25. **No `api()`, no upgrade step.** A site's own `rsvp` model or type keeps the name (`cms_records::types()` leaves the bundled one out), and `lint` already warns.
26. **Tests' helpers** (`tests/run.php`): `rsvp_site($fn)` in `booking_site()`'s style writes `events_item.html` (`render.cms.events` with `title`, `date`, `starts` `20:00`, `places` `40`, `rsvp_until` `2026-11-20 18:00`), makes `eventsdata` with those types (`cms_types::ensure`), binds the listeners this process didn't boot with, and in `finally` drops `rsvpdata` and `eventsdata`, removes the views and unbinds. `rsvp_event($values)` saves an event as an editor would (`cms_store::save_item('eventsdata', 0, …, 'editor')`), ten days ahead unless told. `rsvp_reply($values, $who = 'model')` writes a reply (`'visitor'` through `save_item` with `rsvp::$posting` set). `rsvp_mails($fn)` copies `booking_mails()`. The demo suite reuses `mails()`, `mail_to()`, `login()`, `posts_at_once()` and its main server's `CAFE_SPAM_LIMITS=off`.

## Review Focus

1. **The last place, taken at once, on MySQL.** Two yeses for the one place left post together. Expected: one `going`, one `waiting` (not refused), and the going people never exceed `places`; the table exists before the race, since a new table commits on MySQL. Test: R1 `rsvp: two yeses for the last place at once`.
2. **Promotion's order and idempotence.** Places 10, all going (3, 3, 4); waiting a party of 4 (oldest), then 2, then 1. A going 3 says no. Expected: with 3 free the 4 is skipped, the 2 and the 1 move in, each with one `rsvp.promoted`; the 4 keeps its place at the head of the queue; running `promote_waiting()` again moves nobody and sends nothing. Test: R1 `promotion moves every party that fits, oldest first, once`.
3. **Staff editing the event in the page.** `places` raised in the in-page editor promotes after the commit (the listener, in its own transaction); `places` lowered below the people going moves nobody, emails nobody, and flags every going reply `over_places`; a moved date flags `moved` and the links follow it. Tests: R1 `places raised in the page promotes; lowered moves nobody`, R4 `needs attention: gone, hidden, over places, moved`.
4. **A mail scanner and a leaked link.** A GET or HEAD of the link changes nothing; a cross-site POST is refused; the raw token is in no event, log, record or cache file; the link dies when the event is deleted, hidden or starts, and lives after a `no`. Tests: R2 `a GET to the manage link changes nothing`, `the raw token is in no event, log or cache`, `dead links: gone, hidden, started; a no reply's link lives`.
5. **`already_replied` can't hand over someone's reply or flood an inbox.** A post with an address that replied mails the link only to the reply's address, at most once per 5 minutes, never without a stamp, and the 4th post in an hour is held `slow_down`. Test: R3 `already_replied mails the link to the reply's address only, once per five minutes`.
